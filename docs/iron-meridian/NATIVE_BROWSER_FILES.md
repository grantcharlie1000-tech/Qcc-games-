# Browser file access through recovered callers

The actual content worker reads selected base inputs through recovered stat, owning stream construction, buffering, stream length/read-all/EOF, stream destruction and concrete vector cleanup. `NativeBaseFiles` composes `NativeFileStat`, `NativeStreamConstruction`, `NativeContentStream`, `NativeFileIo` and `NativeReaderLifetime` with the browser provider. This extends the earlier manually assembled handle path. It does not establish a native campaign.

The provider models exactly one explicitly captured loose base folder. Its mount, archiver, IO table, mutex state, allocator and hot TLS state are supplied browser state. Callback tokens are authored identifiers, not recovered executable addresses. Each token, opaque pointer and IO pointer is checked at its callback. The original Windows provider, actual engine mount construction, archive resolution, active DLC/mod selection and cold TLS initialization remain unresolved.

Stat runs before Blob acquisition. It writes a regular-file size from immutable Blob metadata, inferred-directory type, unknown time values and readonly status. Readonly describes this adapter, not original disk permissions. Only the requested regular file is hydrated. A mode-zero owning stream uses a 1 MiB buffer, and read-all fills a native vector. The cursor must reach EOF. Returned bytes own a copy before stream and vector destruction. Hashing and VFS selection still operate on those exact bytes, without CR/string conversion.

Each asynchronous read owns separate memory, TLS, provider cursor and native handle lists. Native size values are checked before conversion to browser offsets. A successful read requires completed stream/vector destruction, balanced locks, an empty handle list and no live native allocations. On failure the adapter attempts each cleanup at most once, still attempts vector cleanup after a stream failure, then discards per-read host memory. Host disposal after a stopped destructor is distinct from successful native cleanup or C++ exception unwinding. Selected content bytes are not written into app saves.

`manifest.fileAccess` records the supplied model, completed reads, stat/open/read/close calls, stream constructions, read-all calls, stream/vector destructions and live handles. These are adapter invocation counts, not executed x64 instruction counts. Empty inputs invoke read-all but skip its engine byte-read branch. Loader identity is `base-loose-explicit-v3`. Input identities still hash returned bytes; the manifest's executable identity does not authenticate an arbitrary selected folder as that executable's effective world.

Eleven adapter tests cover binary bytes, empty files, nonalias output, missing files/directories, concurrency, long paths, Blob failures and reads below/at/above the buffer boundary. Independent integration review passes 25 overlapping main/fault checks, including earlier provider faults and three partial destructor cases. It found the cross-page constant mapping and missing reallocation blockers, both corrected with retained failures. One old short-read injection required adaptation for buffering; its prior failure and the compatible two-byte-then-EOF probe are retained. Node-hosted fault probes are separate from original-instruction and browser evidence.

Current source-bound browser, build and offline evidence is retained under `work/iron-meridian/native-input-integration`: 6,631 tests, full build/TypeScript, explicit offline verification, five production browser tests and sixteen real-installation checks. All 1,087 inputs complete owning stream/vector lifetimes, with zero live handles. [NATIVE_INPUT_STREAM_PORT.md](NATIVE_INPUT_STREAM_PORT.md) links the component evidence. Earlier checkpoints remain preserved. Full-port limits remain in [PARITY_LIMITS.md](PARITY_LIMITS.md).
