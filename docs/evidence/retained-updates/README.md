## Implementation and tradeoffs

The new worker installs a coherent HTML/manifest/entry and every versioned runtime JS/CSS before activation. It can activate over the old worker without reloading any document. Existing clients retain their cached immutable assets; fresh navigation receives current HTML. The first measured atomic pack contained 30 JS/CSS files totaling 978,746 bytes. The UI-verified pack `5a79db6d04b3` contains 30 totaling 982,379 bytes, including 174,367 bytes of entry/CSS; the added runtime download is 808,012 bytes (about 789 KiB). Games still import and mount on demand, but their runtime bytes now download during worker installation. The offline button continues to verify/store the complete versioned pack. Browser policy/eviction can remove offline data.

A new worker reads its predecessor's final durable ownership ledger during activation. Modern navigation persists its reserved client ID before returning HTML. Actual module URL/source-client ACKs identify dependencies; known ready clients omitted by enumeration are checked individually. Unacknowledged/canceled navigation reservations retain only the generation they might use. There is no timeout that silently releases these dependencies. A genuinely untracked legacy cache set is pinned by exact scoped names and propagated across later workers: this deliberately spends storage to protect execution-unready old documents the legacy worker cannot report. Missing/malformed metadata retains conservatively. Later unrelated generations can still be reclaimed. Deletion is limited to the install-time stale snapshot; another scope and a future install with a distinct version key are protected. Same-name concurrent first deletion is an open review finding. Retired candidate names are durably removed before deletion, so later ACKs/restarts do not repeatedly delete a recreated name. Failed retirement persistence prevents deletion; deletion failure can conservatively leak a cache.

The app checks startup/foreground/online, and retries a failed initial inspection/registration. Update notices are accessible in both the game menu and Study, without focus changes. Waiting workers are identified by version/entry before explicit activation. Only a user request reloads; it requires durable game serialization and all pending scores/settings/favourites writes, checked again immediately before reload. New topic intent (including away/back), game navigation or resume cancels an old pending request. Quota/activation refusal leaves the document usable and retains its explanation until retry.
